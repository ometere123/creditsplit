### Source parity: repository LF versus deployed CRLF

The tracked GitHub blob `contracts/Creditsplit.py` uses **LF** line endings: **46,274 bytes**, SHA-256 `26fe312ed90aa6bb918820e19dc8d19584f5eaf3777b08ec1996a7a8b6c077ca`. The deployed source reported by StudioNet `gen_getContractCode` uses **Windows CRLF** line endings: **47,179 bytes**, SHA-256 `309998d18ce351f45af55c34dcab3481c8bb923f74b9d2da5249e0039c3f6977`. There are **905** line endings, accounting exactly for the 905-byte size difference. Converting the tracked LF source to CRLF reproduces the deployed byte length and SHA-256 without modifying any code tokens. Thus the repository and registered source are content-equivalent after line-ending normalization; their **raw bytes are not identical**, and hashing the GitHub file without normalization will not produce the deployed digest.

Reproduce both hashes locally from the tracked file without modifying it (run from repository root):

```python
from pathlib import Path
from hashlib import sha256

source = Path("contracts/Creditsplit.py").read_bytes()
lf = source.replace(b"\r\n", b"\n")
crlf = lf.replace(b"\n", b"\r\n")
for label, payload in (("repository LF", lf), ("deployed CRLF", crlf)):
    print(f"{label}: {len(payload):,} bytes; SHA-256 {sha256(payload).hexdigest()}")
```

This normalization explains the two digests; the recorded on-chain CRLF hash/length are from the deployment RPC evidence, not from a fresh network read in this note. Neither the Python contract nor the deployment was changed for this documentation clarification.

### Independent delivery verification procedure

The repository now includes the read-only [`frontend/scripts/verify-delivery.mjs`](../frontend/scripts/verify-delivery.mjs) utility. It accepts the RPC, contract, project, parent settlement hash, beneficiary addresses and child hashes, then reads the project, parent/child transaction records and current balances. It checks the authenticated contributor or sponsor recipient set, exact wei conservation, parent finality/consensus/leader execution, SDK-decoded settlement method/project ID, and child recipient/value matching. Positive parent/child provenance requires the official GenLayerJS [`getTriggeredTransactionIds`](https://docs.genlayer.com/api-references/genlayer-js/transactions) result to equal the supplied child set; caller-supplied hashes are not accepted as provenance by themselves. Each child is also checked for the expected contract origin, beneficiary, exact amount, terminal status and protocol-reported `value_credited` value.

The verifier supports both contributor payouts and contract-supported refunds. Use `--mode payout`, `--mode refund` or the default `--mode auto`; refund mode checks the sponsor as the sole expected beneficiary, the settlement reason, the original pool and the single exact refund amount instead of requiring contributor allocation arrays. It distinguishes finality, consensus, leader execution, child value credit and independently observed wallet balance. An EOA child with `NO_MAJORITY` is not automatically treated as a failed payment: GenLayer documents EOA sends as finalized external messages, but a child consensus label alone still does not prove beneficiary delivery.

Optional `--before-block` and `--after-block` arguments must be valid chronological block identifiers before the script calculates historical balance deltas. A calculated before/after difference is classified only as an observed, unattributed delta in the current release: the public RPC path does not expose trusted beneficiary activity and gas attribution that the verifier can independently bind to this settlement. Caller-supplied attribution objects are deliberately ignored for positive verification. Missing historical queries, missing child fields, contradictory receipts or unsupported child discovery remain inconclusive rather than passing.
